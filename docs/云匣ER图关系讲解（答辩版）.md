## 0. 开场 30 秒（先把结论扔出来）

> 「我们做的是个人私有云网盘，服务端是 C++17 + SQLite，零第三方依赖。
> 数据层我拆成**两张库**：`users.db` 管账号会话，`cloudvault.db` 管文件业务；
> 文件不是整块存，而是**内容寻址分块**（相同内容只存一份，靠引用计数回收）。
> 一共 **18 个持久化实体 + 1 张结构版本表**，我把它们按业务域切成 8 个模块画了 ER 图，
> 每个模块内部是强关联，模块之间靠 `owner_id` 或内容哈希松耦合。」

一句话记住：**这张 ER 图回答的是「文件怎么存、怎么找回来、怎么安全地分享出去」。**

## 1. 图怎么看（先统一记号，别让老师看懵）

| 图形 | 含义 |
|---|---|
| ▭ 矩形 | **实体**（一张表），主标题是中文名，下面小灰字是英文表名 |
| ◯ 椭圆 | **属性**（字段），主键带**下划线**，外键标「（外键）」 |
| ◇ 菱形 | **关系**（两个实体之间的业务联系），里面是关系动词 |
| 实线 + `1`/`n` | 有明确主外键对应，**基数**标在两端 |
| **虚线** | **跨库/逻辑引用**：数据库里**没有物理外键**，靠代码保证 |

⚠️ 答辩时一定要主动说明：**本项目所有表都没有物理外键**（虽然开了 `PRAGMA foreign_keys=ON`，但建表脚本里没有任何 `FOREIGN KEY`）。级联删除、一致性都是**代码手写**的。这是设计选择，不是漏了。

## 2. 全局设计：两个关键决策

### 2.1 为什么拆成两张库

| 库 | 实体 | 为什么分开放 |
|---|---|---|
| `users.db` | `users`、`sessions` | 账号/凭证是安全边界，可独立备份、独立迁移 |
| `cloudvault.db` | 其余 16 张 | 业务数据，体积大、增长快 |

**代价**：SQLite 无法跨库建约束 ⇒ 两边的联系只剩 `owner_id` 这一个**整数约定**，越权过滤全靠代码（`authUserId >= 1` 时只允许 `owner_id = authUserId`）。

### 2.2 为什么用「内容寻址分块」而不是整文件

`chunk` 表以**内容哈希 `hash` 为主键**，另有 `ref_count` 引用计数：

- **秒传**：上传前先问服务端，分块齐了直接标记完成，不传数据；
- **去重**：同一份内容 N 个用户上传，磁盘只存一份；
- **回收**：`ref_count` 降到 0 才是真正的孤儿块，可被 GC。

**代价**：删文件时磁盘不会立刻释放（引用还在），这也是后面「配额双口径」的由来。

## 3. 逐模块讲关系（核心部分）

### 3.1 模块一 · 账号与会话（m1）

| 关系 | 基数 | 说明 |
|---|---|---|
| `users` —拥有→ `sessions` | **1 : n** | 一个账号可有多台设备/多次登录；`sessions.user_id` → `users.id` |

- `sessions` **只存 `token_hash`**（令牌的 SHA-256），不存明文令牌；
- `token_version` 是「改密/踢下线」的开关：改密码时自增，旧会话全部失效；
- `users.quota_bytes` 是配额上限，`0` 表示不限。

> 讲点：**凭证不落明文 + 版本号批量失效**，这是账号域的两个安全设计。

### 3.2 模块二 · 文件与目录（m2）★ 最重点

| 关系 | 基数 | 说明 |
|---|---|---|
| `dir_node` —所在目录→ `file_dir` | **1 : n** | 一个目录下可以挂多个文件 |
| `file_node` —归属→ `file_dir` | **1 : 0..1** | 文件**可以不属于任何目录**（根目录/历史数据） |
| `file_node` —分块→ `file_chunk` | **1 : n** | 有序分块清单，靠 `seq` 拼装 |
| `chunk` —引用→ `file_chunk` | **1 : n** | 同一块内容可被多个文件共享 |
| `users` —归属用户→ `file_node` | **1 : n**（**跨库虚线**） | `owner_id`，唯一归属判定入口 |

**为什么 `file_dir` 是 `1 : 0..1` 而不是 `1 : 1`？**
因为 `file_dir` 在查询里是 **LEFT JOIN 语义**——历史上有些文件行没有对应的目录行。图上标 `0..1` 是如实反映，不是画错。

**为什么目录不用 `FileNode.parent_id` 自引用？**
我们用 `dir_node(owner_id, path)` **复合主键** + `file_dir` 关联表：
- 路径唯一性由复合主键天然保证；
- 移动文件 = 改 `file_dir` 的一行，不用递归改子树；
- 避免邻接表模型的递归查询。

### 3.3 模块三 · 分块上传会话（m3）

| 关系 | 基数 | 说明 |
|---|---|---|
| `upload_session` —含分块→ `upload_chunk` | **1 : n** | 一次会话收多个分块，`seq` 定序 |
| `upload_session` —目标目录→ `upload_dir` | **1 : 1** | 一次上传只有一个目标目录 |
| `upload_session` —标志→ `upload_flags` | **1 : 1** | 是否覆盖写等开关 |
| `upload_session` ⇢物化→ `file_node` | 逻辑（虚线） | `complete` 时才真正落成文件 |

**断点续传的落点就在这三张表**：会话、已收分块（`sha256`）、目标目录都持久化在库里，进程被 `kill -9` 后重启仍能续传；会话空闲 24h 被 GC 回收。

### 3.4 模块四 · 版本历史（m4）

| 关系 | 基数 | 说明 |
|---|---|---|
| `file_node` —历史→ `file_version` | **1 : n** | 一个文件多个历史快照 |
| `file_version` —快照块→ `file_version_chunk` | **1 : n** | 版本自己的分块清单 |
| `chunk` —引用→ `file_version_chunk` | **1 : n** | 与 `file_chunk` **同构，共享同一批 chunk 行** |

**两个答辩亮点：**
1. **当前内容永远在 `file_node`，`file_version` 只存历史**；列表里第一条是合成的「当前版本」（不是真实行）。
2. **回滚是零拷贝**：只是把某个版本的分块清单写回 `file_node`，不复制任何数据。

### 3.5 模块五 · 标签（m5）

| 关系 | 基数 | 说明 |
|---|---|---|
| `tag` —打标→ `file_tag` | **1 : n** | 一个标签可打在多个文件上 |
| `file_node` —关联→ `file_tag` | **1 : n** | 一个文件可有多个标签 |
| `users` —归属→ `tag` | **1 : n**（跨库虚线） | 标签按用户隔离 |

这是**典型的多对多拆解**：文件 ×× 标签 ⇒ 中间表 `file_tag(file_id, tag_id)` 复合主键。
标签名唯一性由索引 `(owner_id, name COLLATE NOCASE)` 保证——**同用户下不区分大小写重名**。

### 3.6 模块六 · 分享链接（m6）

| 关系 | 基数 | 说明 |
|---|---|---|
| `file_node` —分享→ `shares` | **1 : n** | 一个文件可生成多条分享链接 |
| `users` —归属→ `file_node` | **1 : n**（跨库虚线） | 越权判定走这里 |

⚠️ **`shares` 表没有 `owner_id`**——这是刻意设计：归属完全由 `file_id` 推导，避免冗余字段不一致。
分享有软撤销 `revoked`、次数上限 `max_downloads`、过期时间 `expires_at`。

### 3.7 模块七 · 查杀判定缓存（m7）

| 关系 | 基数 | 说明 |
|---|---|---|
| `file_node` —判定→ `file_scan` | **n : 1** | 按**内容哈希**共享一条判定 |

**为什么是 n : 1 而不是 1 : n？**
因为同一份内容（同 `content_hash`）不管被多少用户上传，查杀结果都一样 ⇒ **缓存一条就够**，省钱又省时。
`verdict` 枚举：`0=未知（未收录，≠安全）`、`1=干净`、`2=可疑`、`3=恶意`。
只发哈希、不发文件内容。

### 3.8 模块八 · 客户端本地持久化（m8）

| 关系 | 基数 | 说明 |
|---|---|---|
| 同步配对配置 —索引→ `sync_index` | **1 : n** | 一个同步配对对应 N 条本地文件索引 |
| 同步配对配置 ⇢映射→ `dir_node` | 逻辑 | `remotePath` 指向云端目录 |
| 分享码缓存 ⇢对应→ `shares` | 逻辑 | 明文提取码**只在创建时返回一次**，客户端自己缓存 |

客户端侧不落在服务端库里：`sync_index` 是独立 sqlite，`sync/pairs`、`share/codes`、`pinnedFingerprint` 三组配置在 `settings.ini`。所以图上用**虚线**表示「跨存储的逻辑引用」。

## 4. 设计取舍（答辩加分项，主动讲）

1. **不用物理外键**：跨库做不到、软删除/墓碑机制与外键冲突 ⇒ 改为事务 + 手写级联（如删标签时手写清理 `file_tag`）。
2. **回收站三态**（一个字段组合表达三种状态）：
   - `deleted=0`：正常
   - `deleted=1 且 deleted_at>0`：在回收站，可恢复
   - `deleted=1 且 deleted_at=0`：**硬删墓碑**，不可恢复
3. **配额双口径**（容易踩坑，务必说清）：
   进站（软删）**磁盘不释放**，但 `sumSizeOfOwner` 带 `WHERE deleted=0` ⇒
   **「已用空间」当场下降，磁盘尚未释放**。只有 `purge` 才真正回收分块。
4. **时间统一毫秒**：所有 `*_at` 是 Unix **毫秒**，且 `0` 有语义（永久 / 未发生 / 墓碑）。
5. **`shares`、`file_scan` 刻意不带 `owner_id`**：前者靠 `file_node` 推归属，后者按内容跨用户共享。
6. **`owner_id=0` 是历史遗留桶**：登录后任何人都看不见，做数据迁移时要特别处理。

## 5. 常见追问 & 标准回答

**Q：为什么数据库里没有外键约束？**
> 两个原因：一是 SQLite 跨库无法建约束，而我们是双库架构；二是回收站/墓碑依赖软删除，物理外键会阻碍删除并打乱级联顺序。一致性改为「单事务 + 代码手写级联」保证，关键操作（删除文件、替换内容、删标签）都在代码里显式处理。

**Q：删了文件磁盘为什么没变小？**
> 进站只是软删除，分块引用计数还没减。设计上「已用空间」（配额口径）立刻下降，但磁盘要等 `purge` 且 `ref_count` 归零才释放。

**Q：秒传怎么实现的？**
> 客户端先算整文件哈希，`init` 时服务端查 `chunk` 表，分块齐备就直接返回完成并物化文件，一个字节都不传。

**Q：多对多关系怎么拆的？**
> 文件×标签拆成 `file_tag(file_id, tag_id)`；文件×目录拆成 `file_dir(file_id, dir)`。中间表用复合主键，天然去重。

**Q：版本回滚会不会占双倍空间？**
> 不会。回滚只是把某版本的分块清单写回 `file_node`，指向的还是同一批 `chunk`，零拷贝。

**Q：目录为什么不用自引用的 `parent_id`？**
> 复合主键 `(owner_id, path)` 能保证路径唯一、移动只改一行、也避免了邻接表的递归查询。

**Q：分享表为什么没有 `owner_id`？**
> 归属由 `file_id` 推导即可，冗余存反而可能不一致；越权判定统一走 `file_node.owner_id`。

**Q：查杀为什么按内容哈希缓存？**
> 同一份内容结果必然一致，按哈希缓存可以让多用户复用同一条判定，减少外部 API 调用（也符合只发哈希、不传文件的隐私设计）。

## 6. 收尾一句

> 「整套 ER 的核心就三件事：**内容寻址**解决存储成本，**owner_id** 解决归属与隔离，**软删除三态**解决误删恢复。
> 所有跨库、跨存储的联系我都用虚线标了出来——那些是**逻辑引用**，不是数据库约束，这也是这套设计最需要小心维护的地方。」
