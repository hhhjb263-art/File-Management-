## 1. 开场定位（0:00–0:30）

> 各位老师好，我的毕业设计是**云匣 CloudVault —— 个人私有云网盘系统**。
>
> 它要解决的是一个很朴素的矛盾：**数据主权和使用便利，目前往往只能二选一。**
> 用公有云网盘很方便，但文件存在别人的服务器上，还有限速和订阅费用；用 Nextcloud 这类重型私有云，数据能自持，但部署要 PHP 加一堆组件，对个人用户来说太重。
>
> 我的目标是做一个**部署在自己的机器上、数据 100% 自有、装完就能用**的轻量网盘。
> 系统定位为单实例 1~20 个用户、十万级文件量。
>
> 代码规模：**服务端 1.35 万行、客户端 2.66 万行，合计约 4 万行 C++ / QML**，51 个 REST 接口，18 个持久化实体。

## 2. 总体结构（0:30–1:30）—— 翻 `output/architecture.png`

> 系统是标准的**客户端 + 服务端**两层，但两边都遵循**严格单向分层依赖**——上层可以调下层，反向一律禁止，这个约定我是靠目录结构和编译期就焊死的。
>
> **服务端**用 C++17 手写，**零第三方库**：HTTP 服务器是 POSIX socket 加线程池自己实现的，元数据存储用 SQLite3，一共 **51 个 REST 接口**。服务端分五层：
> 最底下 `core` 是基础能力——SHA-256、PBKDF2、自写 JSON、日志、配额判定；
> 往上是 `meta` 元数据仓储、`store` 内容寻址落盘、`net` HTTP 服务器，最上面 `app` 做路由装配。
>
> **客户端**用 Qt 6，分七层：最底下 `core`（日志、配置、加解密、路径处理），往上是 `net` 数据源抽象，再往上是 `sync` 同步引擎和 `transfer` 传输队列，然后是 `data` 列表模型、`controllers` 控制器、`app` 应用装配，上面是 QML 界面，一共 9 个页面、11 个控件、10 个对话框。
>
> 这里有一个我比较满意的设计：**`net` 层做成了 Backend 抽象接口**。
> 连远程服务器是 HttpBackend，连本地演示是 MockBackend，**界面层零改动**就能切换数据源——开发时不用起服务器就能调界面，也保证了后续换传输实现不影响上层。

## 3. 功能模块（1:30–3:00）—— 翻 `er-diagrams-chen/overview.png`

> 功能上我按业务域划成**八个模块**，数据库的切分边界和这个划分保持一致：
>
> **M1 账号与会话**——注册登录、PBKDF2 加盐哈希、会话管理、改密并踢出其他会话。
> **M2 文件与目录**——目录树浏览、上传下载、新建、重命名、移动、搜索，这是最核心的模块。
> **M3 分块上传会话**——分块上传、**秒传**、**断点续传**，面向大文件和不稳定网络。
> **M4 版本历史**——自动快照、一键回滚到指定版本。
> **M5 标签体系**——给文件打标签，支持多条件组合筛选。
> **M6 分享链接**——**带提取码**的分享链接，可设有效期和访问次数，随时吊销，并留访问日志。
> **M7 恶意文件判定**——按内容哈希查判定缓存，判定结果可复用。
> **M8 客户端本地持久化**——本地文件索引，是同步引擎的地基。
>
> 界面对应九个页面：文件、传输队列、分享、标签、版本、回收站、同步、设置、登录。

## 4. 三个技术亮点（3:00–4:20）—— 翻 `flowcharts/f3b.png`、`flowcharts/f8.png`

> **亮点一：内容寻址存储，而不是整文件存。**
> 文件被切成固定大小的块，每块按 SHA-256 值落盘，**文件名就是哈希本身**。这带来三个收益：相同内容只存一份、天然去重；**秒传**——客户端先算整文件哈希，服务端发现分块都已存在，直接标记完成，一个字节都不传；以及按块回收。
>
> **亮点二：双向同步，绝不静默丢数据。**
> 这里有三条硬规则。第一，云端删除只进回收站，不真删。第二，**本地删除也不直接抹掉**——先搬到本地的 `sync-trash` 目录保留，如果搬移失败，就逐个回退成"跳过并报错"，绝不在搬移失败的情况下硬删。第三，文件冲突**保留两份，不覆盖**。同步触发是"文件监听防抖 5 秒 + 每 10 分钟全量对账兜底"双保险，防止网络抖动或监听句柄耗尽导致漏事件。
>
> **亮点三：双库 + 归属隔离。**
> 账号会话放在 `users.db`，文件业务放在 `cloudvault.db`，安全边界和业务数据可以独立备份、独立迁移。
> 这里我要**主动说明一个设计取舍**：本项目**没有使用物理外键**，级联删除全部手写在代码里。原因是双库架构下 SQLite 跨库无法建约束；同时回收站依赖软删除，物理外键会阻碍删除并打乱级联顺序。一致性改由"单事务 + 代码显式级联"保证。
> 归属隔离有一条硬规则：登录用户的请求只允许访问 `owner_id` 匹配的资源，**越权一律返回 404 而不是 403**——不泄露这个资源到底存不存在。

## 6. 高频追问预案

| 追问 | 标准回答（三句话内） |
|---|---|
| **为什么不用 Nextcloud？** | 目标是个人和小工作室用户，Nextcloud 的 PHP 多组件部署成本与"单二进制、装完即用"的定位冲突。我选做减法：只保留八个核心业务域，用自研代码换零依赖部署。 |
| **秒传会不会有安全风险？** | 秒传只复用**已存在的分块**，不新建内容，且每次都带归属校验。判定"内容已存在"时不仅查存在性，还校验**尺寸正确**，避免断电留下的 0 字节或截断 blob 被误判为已存在、导致坏内容永久固化且永不重传。 |
| **项目最大的不足是什么？** | 一是端到端测试缺口，服务端在 Windows 编不了；二是客户端上传下载**仍是同步阻塞调用**，大文件传输期间界面会卡顿——这条我在 `src/sync/SyncEngine.h` 头注释里就标注了，解决方案是给 Backend 补异步上传下载变体。 |
| **为什么不用物理外键？** | 两个原因：双库架构下 SQLite 跨库无法建约束；回收站与硬删墓碑依赖软删除，物理外键会阻碍删除并打乱级联顺序。一致性靠单事务 + 显式手写级联保证。 |
| **为什么拆成两个数据库？** | 账号凭证是安全边界，业务数据体积大、增长快，分开可独立备份与迁移。代价是跨库只剩 `owner_id` 这一个整数约定，越权过滤全部靠代码，所以我在 HTTP 层统一加了归属校验。 |
| **怎么保证多用户之间不会互相看到文件？** | `authUserId >= 1` 时所有查询强制带 `owner_id` 过滤，越权一律 404；legacy 的 `owner_id=0` 桶在登录后对所有人不可见。另外会话凭证落哈希不落明文，改密按版本号批量失效。 |
| **同步冲突具体怎么判？** | 决策逻辑抽在 `SyncPlan` 里做纯函数，只回答"该干什么"；执行由 `SyncEngine` 负责。冲突一律保留两份并改名，绝不覆盖。 |
| **为什么服务器不用现成的 HTTP 框架？** | 目标是零第三方依赖、可交叉编译到迷你主机/NAS。代价是要自己处理 HTTP 解析、线程池和连接管理，收益是部署环节没有任何依赖求解问题。 |
