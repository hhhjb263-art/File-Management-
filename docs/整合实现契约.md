# 云匣 CloudVault 正式客户端 · 接口契约（冻结）

> 本文件是 `src/` 各层并行实现的**唯一接口依据**。任何一方需要变更接口，必须先改本文件并通知全体实现方。
> 目标形态：**QML 界面 + 分层 C++**，能力母体为已验证的 `client/`（契约正确），服务端不支持的能力「接口保留、UI 不暴露」。

---

## 0. 分层与依赖规则（禁止跨层反向依赖）

```
qml/  ──调用──▶  controllers/  ──调用──▶  transfer/ · net/ · sync/ · core/
                     │                        ▲
                     └──使用──▶  data/（QML 数据模型）
app/  负责装配：创建 net/transfer/sync + controllers + models，注册到 QML 上下文
```
- QML **只**调用 `controllers/` 与 `data/` 暴露的属性/方法/角色；不直接触碰 `net/`、`transfer/`、`core/`
- `net/`、`transfer/`、`sync/`、`core/` 不 include `controllers/`、`data/`、`qml/`

## 1. `net/` —— 服务端真实契约（由 net 实现方负责）

- 抽象接口 `Backend.h` **保持完整**（产品蓝图不删）；服务端不具备的能力返回 **`Unsupported`** 结果，不发请求
- 契约细节以 `server/README.md` + `server/src/app/main.cpp` 的 `server.route(...)` 为准；调用方式对齐 `client/src/MainWindow.cpp`（唯一已验证实现）
- 统一出口负责：URL 拼装 + 百分号编码、`Authorization: Bearer <token>`、HTTP 状态码与 JSON `error` 映射、**TOFU 证书固定**（首次确认→记住 SHA-256→不一致拒绝；弹窗必须 `exec()`）
- 可识别结果：**同名冲突（409）**、缺块（409 missing）、哈希不符（422）、空间不足（507）、未授权（401）、不支持（本地枚举）

**Unsupported 清单**：登录/用户体系、回收站、版本、分享、标签、搜索、parentId 目录体系（服务端用 `dir` 路径字符串）

## 2. `transfer/TransferManager` —— 传输队列（冻结 API）

职责：分块上传（含秒传、断点续传、并发 3 块）、Range 下载（4 路窗口、按序落盘、断点）、队列与进度。逻辑移植自 `client/src/MainWindow.cpp` 的已验证实现。

```cpp
class TransferManager : public QObject {
    Q_OBJECT
    Q_PROPERTY(int     activeCount    READ activeCount    NOTIFY changed)
    Q_PROPERTY(QString statusText     READ statusText     NOTIFY changed)  // "… 上传中 3/8"
    Q_PROPERTY(bool    busy           READ busy           NOTIFY changed)

public:
    // 上传：本地文件绝对路径列表 → 远端目录（dir 为相对路径，'' = 根目录）
    Q_INVOKABLE void enqueueUpload(const QStringList &localPaths, const QString &dir);
    // 下载：fileId 列表 → 本地保存目录
    Q_INVOKABLE void enqueueDownload(const QStringList &fileIds, const QString &destDir);
    Q_INVOKABLE void cancelCurrent();

signals:
    void changed();
    void taskProgress(const QString &taskId, qint64 done, qint64 total);   // 进度
    void taskFinished(const QString &taskId, bool ok, const QString &message);
    void conflictDetected(const QString &taskId, const QString &dir, const QString &name);
    // ↑ 同名冲突：由 TransferController 弹"是否覆盖"，再回调解续
    void logMessage(const QString &level, const QString &text);

public slots:
    void resolveConflict(const QString &taskId, bool overwrite);   // 覆盖=true / 跳过=false
};
```

**关键实现约束**（都是踩过的坑，务必保留）
1. 分块上传：`init` → 3 块并发 `PUT chunk`（带 `X-Chunk-SHA256`）→ `complete`；秒传（`done:true`）直接完成
2. **本地 manifest** 记录 `size/mtime/full_hash` 三者一致才续传；`complete` 成功后删除
3. Range 下载：**4 路并发窗口**，乱序到达先缓存、**按序落盘**（写盘串行化，防写坏 `.part`）；`.part` 追加语义保证断点有效
4. 大文件哈希与读块**必须离开 UI 线程**（用 `QThreadPool`/`QtConcurrent`）；工作线程只碰值拷贝，结果经 `QMetaObject::invokeMethod(..., QueuedConnection)` 回主线程
5. 内存与文件大小解耦：绝不整文件读入内存（整文件只走 ≤ 8 MiB 的小文件路径）

| 模型 | 角色（roleNames） |
|---|---|
| `FileListModel` | `name` `size` `time` `status` `id` `dir`（`id/dir` 供右键菜单使用，界面可不显示） |

### 4.1 角色语义（**冻结，QML 必须按此绑定**）

`FileListModel`
| 角色 | 类型 | 语义 |
|---|---|---|
| `name` | string | 文件/目录名 |
| `size` | **string（已格式化）** | 展示用，如 `1.23 MB`（对齐母体 `formatSize`） |
| `sizeBytes` | qint64 | **原始字节**（排序/逻辑判断用它） |
| `time` | **string（已格式化）** | 展示用，如 `2026-09-17 08:22`（对齐母体 `formatTime`） |
| `mtime` | qint64 | 原始时间戳 |
| `status` | string | 秒传标记：`是` / `否` / `-`（对齐母体 instantText） |
| `id` | string | 文件 id；目录可用合成 id |
| `dir` | string | 所属目录（相对路径，`""` = 根目录） |
| `hash` | string | 内容哈希（默认不显示） |

> ⚠️ **QML 注意**：`size` 与 `time` 是**字符串**，直接绑定即可显示；需要参与计算/比较时用 `sizeBytes` / `mtime`。

`TransferModel`
| 角色 | 类型 | 语义 |
|---|---|---|
| `taskId` | string | 任务标识 |
| `fileName` | string | 文件名 |
| `kind` | string | `upload` / `download` |
| `done` / `total` | qint64 | 已完成/总字节 |
| `progress` | int | **0..100**（百分比整数） |
| `progressRatio` | double | **0.0..1.0**（`ProgressBar.value` 推荐用它，因为该控件默认区间是 0–1） |
| `state` | string | 逻辑用英文 token：`queued`/`hashing`/`running`/`paused`/`completed`/`failed`/`canceled` |
| `stateText` | string | 显示用中文（如"传输中"） |
| `message` | string | 附加信息/错误文本 |

**排序在模型内完成**（`FileListModel::sortBy(int key, bool asc)`，key 0=名称 1=大小 2=时间；行为已对齐母体 `applySort`），**QML 不做排序**。
**模型只在主线程读写**（网络/IO 结果须经信号回主线程后再改模型），全程无锁。

## 8. 决策记录（lead 裁决，全体实现方遵守）

### 8.1 删除语义：`purge()` = 真实永久删除；回收站一族 = unsupported
- **裁决**：`purge(id)` **映射到真实接口 `DELETE /api/v1/files/{id}`**（服务端该接口即"删除并回收空间"，返回 `freed_bytes`）；`moveToTrash`/`restore`/`listTrash`/`emptyTrash` 一律 `unsupported`（服务端无回收站）。
- **理由**：若严格按字面把 `purge` 也列为 unsupported，正式客户端将**没有任何删除路径**，与产品能力不符。服务端语义是"硬删除"，故用 `purge` 承载它最贴切。
- **UI 影响**：文件右键"删除"= 真实删除；文案必须明确「删除后不可恢复」（因为服务端没有回收站）。

### 8.2 分块上传的"同名覆盖"：新增**加法式**接口（不改既有签名）
- **问题**：`Backend.h::beginUpload(parentId,name,size,sha256)` 不携带 `overwrite`，导致分块上传只能把 409 当错误、无法覆盖。
- **裁决**：在 `Backend.h` **新增一个带默认实现的虚函数**（对既有实现零破坏）：
  ```cpp
  // 上传同名文件时是否覆盖（仅对"整文件上传"与"分块 init"生效）。默认 false。
  virtual void setUploadOverwrite(bool enabled) { (void)enabled; }
  ```
  - `HttpBackend` 存储该标志：① 整文件上传 → 头 `X-CV-Overwrite: 1`；② 分块 `init` body → `"overwrite": true`
  - `MockBackend` 继承默认实现（no-op），**不需要改**
- **调用方约定（`TransferManager`）**：收到 `conflictDetected` → 上层 `resolveConflict(taskId, true)` 时，先 `backend->setUploadOverwrite(true)`，其余情况保持 `false`；一次覆盖只对随后的那一次上传生效，用后立即复位。

### 8.3 TOFU 确认框：net 层不弹窗，由界面注入回调（QML）
- `src/net/HttpBackend` **不依赖 QtWidgets**（正式客户端链接里没有 Qt6Widgets）。它暴露 `setTrustPrompt(回调)` 由界面层注入确认逻辑；**未注入回调时一律 fail-closed（拒绝连接）**，绝不静默信任。
- **唯一注入者 = `AppController`**：它在构造时调用 `installTrustPrompt()` 注入回调，并通过 `trustPromptRequested` / `answerTrustPrompt(bool)` 与 QML 交互（内部有 `receivers()==0` 守卫，无人接线即拒绝）。
- ⚠️ **`HttpBackend::setTrustPrompt()` 是「赋值」语义，不是追加** —— 全工程**只允许一个注入者**。装配层（`app/Application`）**不得**再次注入，否则后注入者会覆盖前者，导致 QML 只连到其中一条、另一条成为死路径（此缺陷已发生过一次：曾出现"弹窗永不出现 + fail-closed 拒绝连接"）。
- **QML 侧义务**：`CertPinDialog` 绑定 **`App.trustPromptRequested`**，回答时调 **`App.answerTrustPrompt(bool)`**——首次连接展示 `host:port` + 分组指纹(SHA-256) + subject/issuer/有效期；选"信任"→ 写入 `pinnedFingerprint/<host:port>` 并放行；选"不信任"→ 拒绝；**指纹不一致 → 警告且不提供"继续"**。不要再连 `Core.*`（`Application` 的同名 API 已删除）。
- 指纹持久化文件与 `client/` **不同**（正式客户端用 `AppPaths::settingsFile()`），两者不共享信任记录——这是预期行为，文档需说明。

### 8.4 覆盖同名文件**必须原子**：禁止"先删再传"
- **问题**：`TransferManager` 初版把"覆盖"实现为 `purge(file_id)` 删除旧文件 → 再重新 `init` 上传。这是**两步非原子操作**：若中途失败/断电，用户会**永久丢失原文件**（服务端无回收站，删了就没了）。
- **裁决**：覆盖一律走**服务端原子覆盖语义**：
  - 整文件上传：请求头 `X-CV-Overwrite: 1`
  - 分块上传：`init` body 带 `"overwrite": true`（会话在 `complete` 时替换同名记录内容，失败时旧文件保持不变）
  - 触发方式：`backend->setUploadOverwrite(true)` → 重新发起该次上传 → **发起后立即复位为 false**
- **禁止**：任何形式的"先删旧文件再传新文件"覆盖实现。

### 8.5 分块大小：**单一来源**，由后端暴露
- **问题**：`TransferManager` 用常量 5 MiB 计算 offset→seq，而 `HttpBackend` 从 `Settings::chunkSizeMB()` 取块大小（可被用户改动）。两者一旦不一致，`putChunk` 会被服务端判 400（seq 与 offset 不匹配）。
- **裁决**：在 `Backend.h` 新增（带默认实现，加法式）：
  ```cpp
  virtual qint64 chunkSize() const { return 5 * 1024 * 1024; }   // 分块上传的块大小（字节），唯一来源
  ```
  - `HttpBackend` 覆盖它，返回**它 init 时实际使用**的块大小；并且 **init 直接用该返回值**，不再从 `Settings::chunkSizeMB()` 读取（避免留下一个会让两端失配的隐藏旋钮）
  - `TransferManager` 的 offset 步长 / seq 推导一律使用 `backend->chunkSize()`，不再硬编码
