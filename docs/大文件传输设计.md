# 云匣 CloudVault 大文件传输设计（流式 / 分块）

> 目标：**内存占用与文件大小解耦**。无论 1 KB 还是 2 GB，服务端单次内存峰值都控制在
> 「一个分块/一个 Range 段」量级（数 MiB），不再出现「一次性加载整个文件 → 内存爆炸」。

## 1. 适用场景

| 场景 | 大小阈值 | 走哪条路径 | 内存占用 |
|---|---|---|---|
| 客户端上传小文件 | ≤ 8 MiB | 整文件 POST `/api/v1/files`（`readAll()`） | ~文件大小（≤8 MiB，可接受） |
| **客户端上传大文件** | **> 8 MiB** | **自动转分块流式上传** `/api/v1/uploads/*`（5 MiB/块） | **~1 个分块（5 MiB）** |
| **客户端下载（全部）** | **任意大小** | **Range 分段**，每次只拉 4 MiB，追加写 `.part` | **~1 个 Range 段（4 MiB）** |
| 服务端接收整文件 | > 64 MiB | 直接 **413** 拒绝，提示改用分块上传 | 无（拒绝前不缓冲整文件之外的额外内存） |
| 服务端回发整文件 | 无 Range 且 > 8 MiB | 直接 **409** 拒绝，提示改用 Range | 无 |
| 服务端按 Range 回发 | 任意 | 按分块 `seek` 只读请求区间 | ~1 个分块 |

**结论**：只要任一端走分块/分段路径，内存峰值就与文件总大小无关。

## 2. 传输流程

### 2.1 大文件上传（客户端 > 8 MiB 自动切换）

```
prepareChunkPlan(path)          # 流式算整文件 SHA-256（1 MiB 缓冲），只记录分块表，不载入文件
  ↓
POST /api/v1/uploads/init       # {name,size,chunk_size,hash,dir}；同 hash 命中 → 秒传 done:true
  ↓
for 缺失 seq: PUT /:id/chunk/:seq   # 每块 makeChunk 时 seek+read 5 MiB，逐块发送
  ↓                                  # 2~4 并发，每块带 X-Chunk-SHA256，失败指数退避重试
POST /api/v1/uploads/:id/complete   # 服务端按 seq 顺序拼接 + 校验整文件哈希 → 落内容库 + 镜像文件树
```

关键点：
- **本地不 load 整文件**：`prepareChunkPlan` 用 1 MiB 缓冲流式算哈希；`readChunk(seq)` 用 `seek + read` 只读该块。
- **服务端不 load 整文件**：`PUT chunk` 单请求体就是 1 个分块（5 MiB）；`complete` 逐块读入再拼接写入内容库（流式算哈希），峰值 ≈ 1 块。
- 批量上传队列里，大文件会自动切到这条路径（`kStreamUploadThreshold = 8 MiB`），小文件仍走整文件 POST。

### 2.2 大文件下载（客户端统一 Range 分段）

```
offset = 已有 .part 大小（断点续传）
  ↓
GET /content  Range: bytes=<offset>-<offset+4MiB-1>     # 有界 Range！
  ↓  206 + Content-Range
校验 Content-Range 起点 == 本地 offset  →  追加写入 <file>.part  →  offset += 实际字节
  ↓  未下完则继续下一段
offset >= total  →  校验大小  →  rename .part → 最终文件
```

关键点：
- **必须有界**：只发 `bytes=start-` 会让服务端把「start 到文件尾」全部回发，大文件同样撑爆内存；
  因此客户端恒定发送 `bytes=start-end`（每段 4 MiB）。
- 服务端 `readRange` 按分块 `seek` 只读该区间，不回读整个文件。
- 空文件（total=0）不发 Range，走 200 空响应。

## 3. 内存占用控制策略

| 位置 | 措施 | 峰值 |
|---|---|---|
| 客户端 · 算哈希 | `prepareChunkPlan` 1 MiB 缓冲流式 `QCryptographicHash` | 1 MiB |
| 客户端 · 上传 | 分块按需 `seek+read`（5 MiB）；≤8 MiB 才 `readAll()` | ≤5 MiB（大文件）/ ≤8 MiB（小文件） |
| 客户端 · 下载 | 有界 Range，每段 4 MiB，直接追加落盘 | ≤4 MiB |
| 客户端 · 日志 | 二进制只打「大小 + 前 48 字节 hex」；文本最多前 4096 字符 | 常数 |
| 服务端 · 收分块 | 单请求 = 1 块（5 MiB）；落 `<dataDir>/tmp/uploads/<id>/<seq>.part`（先 .tmp 再 rename） | 5 MiB |
| 服务端 · complete | 逐块读取拼接；`Sha256` 流式 update | ~1 块 + 拼接缓冲 |
| 服务端 · 内容库 | 内容寻址，写 blob 时按块落地 | ~1 块 |
| 服务端 · 回发 | `readRange` 只读请求区间 | ~1 块 |
| **服务端 · 兜底拒绝** | 整文件上传 > 64 MiB → **413**；无 Range 下载 > 8 MiB → **409** | 无额外占用 |

> 兜底拒绝是最后一道闸：即使客户端没走分块/分段路径，服务端也不会因为一个大 body / 一次全文
> 回发而把内存吃满。

## 4. 异常与中断处理

| 异常 | 检测点 | 处理 |
|---|---|---|
| 上传分块失败 | 客户端 `PUT` 非 200 / 网络错误 | 单块指数退避重试（0.5/1/2s，最多 3 次）；耗尽 → 中断会话、**保留 upload_id 与已传分块**供续传 |
| 客户端崩溃 / 进程被杀 | 重启后读本地 manifest | `size + mtime + hash` 三者一致才复用；`GET /uploads/:id` 确认会话仍在（404 则重新 init），只补缺失分块 |
| 服务端重启 | 启动期 GC + init 校验 | 会话/分块记录在 SQLite（真相源）；init 时以 **DB + 磁盘 `.part` 双重校验**自愈，剔除丢失/大小不符的块 |
| 分块内容损坏 | `complete` 校验 | 服务端逐块实测 sha256 与记录比对 → `422 {invalid:[...]}` 精确坏块，客户端只重传坏块 |
| 整文件哈希不符但各块正常 | `complete` 校验 | `422 {invalid:[], reason}`（客户端声明 hash 有误）→ 客户端**终止重传**并提示，避免死循环 |
| 缺块完成 | `complete` | `409 {missing:[...]}` → 客户端补传缺失分块 |
| 上传 > 1 TiB（sanity 上限） | `init` | `413` 总量超限 |
| 上传 > 64 MiB 且未走分块 | `POST /files` | `413` + 提示改用分块接口 |
| 下载中断（网络闪断） | 客户端 Range 段失败 | 终止本次会话、**保留 `.part`**；下次同一目标自动从 `.part` 大小继续 |
| 下载响应起点不符 | 客户端校验 `Content-Range` 起点 | `start != 本地 offset` → 立即终止（防写坏 `.part`） |
| 下载段数与大小不符 | `finalizeDownload` | `.part` 大小 != total → 记日志告警（不静默重命名为正式文件） |
| 空文件 / 单分块 | 两侧边界 | 空文件不发 Range / 跳过分块校验；单分块只有末块分支 |
| 服务端磁盘满 | 上传前预检（整文件 / 分块 init） | **507** + `need_bytes`/`free_bytes`，客户端弹窗告警；写 `.part` 失败仍返回 5xx |
| 镜像文件树失败 | `complete` / 上传 / 新建 / 重命名 | 按分块 blob 拼接（`materializeFromChunks`）；拉不到块则 WARN 并保留 blob+DB 权威（按路径下载不受影响） |
| 会话闲置 | 服务端 GC（>24h） | 清理会话与临时分块；分块 PUT 会刷新 `updated_at`，活跃会话不会被误删 |
| 取消 | 客户端【取消上传】 | `DELETE /uploads/:id` 丢弃会话；批量上传时取消会终止整批 |

## 5. 阈值总览（两侧一致）

| 常量 | 位置 | 值 | 含义 |
|---|---|---|---|
| `kChunkSize` | 客户端 | 5 MiB | 分块大小（与服务端 `chunk_size` 契约一致） |
| `kStreamUploadThreshold` | 客户端 | 8 MiB | 超过则自动转分块流式上传 |
| `kDownloadChunkSize` | 客户端 | 4 MiB | 每次 Range 拉取上限 |
| `kHashBufferSize` | 客户端 | 1 MiB | 流式算哈希的读缓冲 |
| `kMaxUploadBytes` | 服务端 | 64 MiB | 整文件单请求上限（超出 413） |
| `kMaxSingleShotDownload` | 服务端 | 8 MiB | 无 Range 整文件回发上限（超出 409） |
| `kMaxChunkedBytes` | 服务端 | 1 TiB | 分块上传总量上限（sanity 上限；4 GiB+ 可正常传） |
| `kMaxRangeSpan` | 服务端 | 16 MiB | 单次 Range 响应跨度上限（防 `bytes=0-` 撑爆内存） |
| `kSpaceSafetyFactor` | 服务端 | 2 | 上传前空间预检倍数（临时分块 + 内容库并存，峰值 ≈ 2× 文件大小） |
| `kSpaceMarginBytes` | 服务端 | 64 MiB | 空间预检余量 |
| `kMinChunk/kMaxChunk` | 服务端 | 64 KiB / 64 MiB | `chunk_size` 允许区间（clamp） |

## 6. 已知限制

- 服务端 `net` 层的响应体仍是「一次性 `std::string` 缓冲」（`resp.body` 模型），因此**单次回发**
  仍受 8 MiB 限制；真正的分块流式响应需要在 net 层引入流式写接口，属后续工作。
- 分块上传的 `complete` 阶段会把分块逐个读入拼接（峰值 ≈ 1 块 + 拼接缓冲），未做「零拷贝拼接入库」。
- 客户端批量上传为**顺序执行**（不并发多文件），避免并发大文件同时占用多份分块缓冲。
