**一句话定位**：做部署在自有机器上、**单二进制零依赖、数据 100% 自持**的轻量个人网盘，面向个人与 1~20 人小工作室。

**三条底线原则**（被问"为什么这么设计"时的通用回答）：
1. 内容寻址 → 相同内容只存一份（秒传/去重/按块回收）
2. 同步绝不静默丢数据 → 软删除 + 双份保留 + 显式冲突策略
3. 越权一律 404 → 不泄漏"资源是否存在"

## 2. 逐章讲解要点（每章 3~5 个"必须说清"）

### 第1章 绪论（30 秒）
- 矛盾点：**数据主权 vs 使用便利**——公有云方便但文件在别人服务器上，私有云自持但部署太重。
- 定位：单实例 1~20 用户、十万级文件量、**单二进制零依赖**。
- 研究内容一句话：把"内容寻址分块 + 双向同步 + 归属隔离"三件事在轻量部署下跑通。

### 第2章 关键技术介绍（30 秒）
- 选型逻辑一句话：**每一项都服务于"零依赖 + 跨平台 + 轻量"**。C++17 是为了无运行时；Qt 6 是为了一套代码出桌面 GUI；SQLite 是为了单文件库、免部署；QML 是为了声明式 UI。
- 不展开技术细节，**这是第2章不是答辩重点**，一句带过，把时间留给第4、5章。

### 第3章 系统分析（30 秒）
- 可行性四段各一句：技术（Qt6+SQLite 可支撑）/ 经济（零许可费）/ 社会（数据合规与隐私）/ 操作（9 个页面覆盖全部需求）。
- 功能需求按**普通用户 + 管理员**两栏讲；非功能需求给出可验证指标（见 §5.6 性能测试口径）。

### 第4章 系统设计（1 分钟，本次答辩的图纸段）
- **架构设计** → 翻 `output/architecture.png`：两端 + 严格单向分层依赖（`app → store/meta/net → core`），靠目录结构和编译期约束焊死。
- **功能结构** → 翻 `output/er-diagrams-chen/overview.png`：8 个模块 = 数据库切分边界，一一对应。
- **数据库设计** → 翻 `output/er-diagrams-chen/all.png`：18 实体；讲三件事——① 双库（`users.db` / `cloudvault.db`）；② 内容寻址分块（`chunk` + `file_chunk`）；③ 跨库只有 `owner_id` 整数约定 + 虚线弱联系。
- **主动说取舍**（加分项）：本项目**不使用物理外键**，级联全手写，理由见 §5.2。

### 第5章 系统实现（1 分 30 秒，代码段）
- 讲法：**"分层是骨架、模块是肉"**。每个模块只讲"它解决什么难题"（3.1~3.4 的四类难题），不念代码。
- 四个必讲实现点：
  1. **秒传与断点续传**（`f3b.png`）：差集上传 + 会话已建立判据。
  2. **零拷贝回滚**（`f4.png`）：回滚只改写分块清单。
  3. **两级并发**（`f3.png` / §5.3）：文件级 4 × 块级 3 = 最多 12 在途。
  4. **越权 404 + TOFU**（`f1.png`）：安全边界。
- 被要求"看代码"时：`src/transfer/TransferManager.cpp`（并发/断点）、`server/src/store/content_store.cpp`（落盘屏障）、`server/src/app/main.cpp`（路由与归属过滤）。

### 第6章 系统测试（40 秒）
- 讲法：**先讲方法，再讲边界**。方法 = 自动化回归 + 人工功能测试 + 压力 + 安全。
- 密码学部分用**公开标准向量**验证（不是自己和自己比）——这句必须说。
- 边界诚实说：服务端基于 POSIX socket，Windows 上无法编译运行，**端到端 HTTP 用例与 GUI 交互用例尚未执行**；已验证的是纯逻辑层、元数据层、构建纪律层。

## 3. 八大模块速讲（每个模块三句话：功能 / 目的 / 预期）

| 模块 | 功能 | 设计目的 | 设计预期 |
|---|---|---|---|
| **M1 账号与会话** | 注册登录、会话签发与失效、TOFU 指纹固定 | 自建服务无公网 CA，"信任谁"必须先于"是谁" | 口令库泄露不可反推明文；改密后旧会话立即失效 |
| **M2 文件与目录** | 目录树浏览、上传下载、重命名移动、预览 | 列表是停留最久的界面，必须"刷新不打断" | 乱序回包被序号丢弃，旧数据不覆盖新数据 |
| **M3 分块上传会话** | 分块上传、秒传、断点续传 | 大文件整包传输内存不可控且断电全损 | 内存与文件大小解耦；抖动最多重传一块 |
| **M4 版本历史** | 自动快照、一键回滚 | 误删误覆盖是最高频投诉，软删除+快照把不可逆变可逆 | 回滚零拷贝，不产生第二份数据 |
| **M5 标签体系** | 自定义标签、多条件筛选 | 分类检索需要稳定的多对多关系 | 同用户标签名不区分大小写唯一 |
| **M6 分享链接** | 带提取码的公开链接、有效期/次数上限、吊销 | 需要"不交账号也能给文件"的轻量通道 | 明文提取码只出现一次，服务端只存哈希 |
| **M7 恶意文件判定** | 按内容哈希查杀、结论缓存、阈值判定 | 只发哈希不发内容，隐私与成本兼顾 | 同内容多用户只查杀一次，结论可复用 |
| **M8 客户端本地持久化** | 本地索引（`sync_index`）、同步配对配置 | 同步对账的地基，没有索引只能全量扫描 | 索引与指纹比对结合，漏事件由全量对账兜底 |

## 4. 深挖追问预案（按主题分类，每题三句话内答准）

### 4.1 架构与工程
- **Q：为什么不用现成的 HTTP 框架/云存储 SDK？**
  A：目标是零第三方依赖、可交叉编译到迷你主机/NAS。代价是自己处理解析、线程池与连接管理，收益是部署没有依赖求解问题。
- **Q：分层单向依赖怎么保证不被破坏？**
  A：靠目录结构与构建配置（`app → store/meta/net → core`），反向引用在编译期就报错；再叠加一条构建注册检查脚本防漏登记。
- **Q：Backend 抽象是多余的抽象吗？**
  A：它让 `HttpBackend`（真实服务）与 `MockBackend`（本地演示）可互换，界面层零改动，开发时不用起服务器就能调 UI，也为后续换传输实现留了口子。
- **Q：代码有多少是你写的？**
  A：服务端全部自研（HTTP、JSON、SHA-256、PBKDF2、SQLite 封装、日志、配额）；客户端第三方只用了 Qt 6（含 Qt Sql 承载本地索引 `sync_index`）与 SQLite，业务代码自研。第三方只用于 Qt 和 SQLite 这类基础设施。
- **Q：为什么没有 CI？**
  A：目前用本地门禁脚本替代（构建注册检查、harness 离线断言、密码学标准向量），CI 是后续工作。

### 4.2 数据库与存储
- **Q：为什么拆两个库？** 答见 5 分钟稿 §6 同题。
- **Q：为什么不用物理外键？** 答见 5 分钟稿 §6 同题（双库跨库限制 + 软删除墓碑机制）。
- **Q：没有外键，级联怎么保证不漏？**
  A：级联写在代码里，且集中在仓储层（删除标签手写清理 `file_tag`、删除文件手写清理 `file_chunk`），关键操作包在单事务内；测试用例专门覆盖"删标签后关联行是否残留"。
- **Q：目录为什么不用 `parent_id` 自引用？**
  A：用 `dir_node(owner_id, path)` 复合主键 + `file_dir` 关联表。好处是路径唯一性由主键直接保证、移动目录只改关联表一行、避免递归查询。
- **Q：`file_dir` 里的文件可以不属于任何目录吗？**
  A：可以，这是刻意的。`file_dir` 在查询中是 LEFT JOIN 语义，历史数据与根目录文件都能被完整表示。
- **Q：为什么所有时间字段都是毫秒整数？**
  A：统一存储、避免时区歧义；`0` 有明确语义（永久 / 未发生 / 硬删墓碑），不与真实时间混淆。
- **Q：删除文件后磁盘为什么没变小？**
  A：进站（软删除）不释放磁盘，只让"已用空间"这个配额口径下降（`sumSizeOfOwner` 带 `WHERE deleted=0`）；磁盘要等彻底删除且分块引用计数归零才真正释放。**这是两个口径，别混说。**
- **Q：数据库迁移怎么做？**
  A：`migrateSchema` 先跑、再执行建表脚本（`IF NOT EXISTS`），每步用"表存在且缺列"双守卫；顺序反了老库会因为空操作永远补不上缺失列。
- **Q：SQLite 并发写会不会锁冲突？**
  A：服务端写操作集中、事务粒度小，配合 WAL 与忙等重试；元数据层对同一文件的写操作串行化。

### 4.3 传输与大文件
- **Q：分块多大？**
  A：客户端按 5 MiB 切块（服务端上限允许到 64 MiB）；整包上传单请求上限 64 MiB，超过必须走分块协议，避免服务端把整个 body 读进内存。
- **Q：秒传会不会有安全风险？** 答见 5 分钟稿 §6 同题（**并补一句**：判定"内容已存在"时同时校验尺寸正确，避免断电留下的 0 字节 blob 被误判为已存在、导致坏内容永久固化）。
- **Q：断点续传的状态存在哪？**
  A：服务端在 `upload_session`/`upload_chunk`（含每块 sha256），客户端在 `settings.ini` 的上传清单；**进程被杀或断电后重启仍可续传**，会话空闲 24 小时被 GC。
- **Q：为什么合并要两遍？**
  A：第一遍只读校验并逐块重算 sha256，第二遍才落库，落库前先 fsync 形成断电屏障，避免"校验时通过、写入时断电"留下半截文件。
- **Q：下载为什么用 Range？**
  A：整文件下载超过 8 MiB 就不允许单次响应，客户端必须用 Range 分段拉，单次跨度上限 16 MiB，保证服务端内存有界。
- **Q：并发是怎么定的？**
  A：两级调度——文件级并发 4、块级并发 3，最多 12 个在途请求。定这个数的依据是 8×20 线程压测下不出现请求堆积与超时。
- **Q：并发引擎有没有竞态？**
  A：每个任务带 `gen` 世代号，回包必须世代匹配才被接受；`m_cur` 指针只在任务回调链内有效，UI 方法一律按 `taskId` 定位，避免悬垂指针。
- **Q：暂停/继续/取消的状态机？**
  A：暂停保留断点可恢复；取消是真放弃（清断点、不再自动续传）；失败块进入退避重试队列，超过上限才判定任务失败。
- **Q：为什么还有明文镜像树 `files/`？**
  A：可关（`mirror=off`）。开着是为了本机直接访问/备份方便；关掉后内容库是唯一权威副本，下载回落到分块读取。镜像写失败会导致目录操作失败，所以建父目录那段有真实踩坑注释。

### 4.4 同步
- **Q：怎么发现变更？**
  A：双保险——文件监听防抖 5 秒做增量，加每 10 分钟全量对账兜底，防止网络抖动或监听句柄耗尽漏事件。
- **Q：冲突怎么判、怎么解？**
  A：判定抽在 `SyncPlan` 里做纯函数，只回答"该干什么"；执行由 `SyncEngine` 负责。冲突一律**保留两份并改名，绝不覆盖**。
- **Q：本地删除了会不会被同步成"云端也删"？**
  A：不会直接删。本地删除先搬进 `sync-trash/<pairId>/<时间戳>/`；**搬移失败就逐个回退成"跳过并报错"，绝不在搬移失败时硬删**。
- **Q：同步索引丢了会怎样？**
  A：会把全部文件判为"新增"并重复上传。所以 `LocalIndex` 必须先 `open` 再交给 `SyncController`，这是实现里踩过的坑。
- **Q：两端都在改怎么办？** 答：显式冲突策略（保留本地 / 覆盖云端 / 两者都留），默认两者都留。

### 4.5 安全
- **Q：口令怎么存？**
  A：PBKDF2-HMAC-SHA256，每用户独立盐，21 万轮迭代；服务端只存派生值与轮数，**不存明文**。
- **Q：会话怎么管理？**
  A：会话只存 token 的 SHA-256；`token_version` 改密时自增，旧会话整体失效；过期与撤销都在服务端判定。
- **Q：自建 HTTPS 的证书怎么办？**
  A：TOFU（首次使用信任）——首次连接弹出指纹确认，确认后把指纹钉在 `settings.ini`；之后证书指纹变了就拒绝连接，必须用户在设置页显式改。
- **Q：TOFU 会被中间人骗吗？**
  A：首次连接确实无法防御主动中间人，这是 TOFU 的固有代价；它的价值是把"每次都警告"变成"只在证书变更时警告"，并且我把这一点作为局限明确写在论文里。
- **Q：为什么越权返回 404 而不是 403？**
  A：403 等于确认"这个资源存在但你没权限"，本身就是信息泄漏。统一 404 后，无法通过状态码区分"不存在"与"不是你的"。
- **Q：分享提取码怎么保护？**
  A：服务端只存 `code_hash`，明文**仅在创建响应（201）里出现一次**，列表接口永不返回明文；客户端把它缓存到本机 `settings.ini` 供列表回显。
- **Q：分享次数怎么防超发？**
  A：条件原子自增（`UPDATE ... WHERE downloads < max`），并发下不会超发；判定失败**不消耗次数**。
- **Q：病毒查杀会上传文件吗？**
  A：不会，只发内容哈希；判定结论按哈希缓存，同内容多用户共享一条结论。阈值是唯一判定权威，代码里不允许先判"恶意"再拦截。
- **Q：查杀没收录怎么办？**
  A：未收录（404）是**有效结论但不等于安全**，`verdict=0` 表示未知；未启用或网络异常时按策略处理并记日志。

### 4.6 前端与测试
- **Q：界面为什么用 QML？**
  A：声明式便于做主题与响应式；同一套控制器能出桌面 GUI，后续做移动端只需换壳。
- **Q：预览会不会卡住列表？**
  A：预览走异步取流（`requestPreview` 带序号），与列表刷新共用"旧回包作废"机制，绝不阻塞列表交互。
- **Q：测试怎么做的？**
  A：可离线运行的 harness（14 个，共 660+ 条断言），密码学用**公开标准向量**验证（不是自己和自己比），并发上限用真实多线程压测，数据库迁移做红→绿对照复现根因。
- **Q：端到端为什么没测？**
  A：服务端基于 POSIX socket，Windows 上只能做语法级编译，无法运行，因此 HTTP 端到端与 GUI 交互用例尚未执行。已验证的是纯逻辑层、元数据层与构建纪律层——**端到端验收是明确的空白，也是我后续第一优先级的补齐项**。
- **Q：怎么防止漏登记源文件？**
  A：有一条构建注册检查脚本（`scripts/check_build_registration.py`），历史上确实出过一次漏登记导致链接期一堆 undefined reference 的事故，这条防线一直在生效。

## 5. 高风险质疑与应对（照原话说，别临场编）

| 质疑 | 应对（诚实 + 有据） |
|---|---|
| "这不就是 Nextcloud 的简化版？" | 定位不同：Nextcloud 是多组件协同平台，目标是团队协作；我做的是单二进制、零依赖、面向个人与小工作站的轻量网盘，并且把内容寻址、秒传、零拷贝回滚、双向同步冲突策略做成了明确的工程目标。请老师指出哪一块超出我的实现范围，我按代码说明。 |
| "没有物理外键，数据库设计是不是不严谨？" | 这是有意识的取舍，不是遗漏。理由两条：双库下 SQLite 跨库无法建约束；回收站的软删除与硬删墓碑依赖 `deleted`/`deleted_at` 组合表达，外键会阻碍删除并打乱级联顺序。一致性由"单事务 + 仓储层显式级联"保证，并有专门的测试覆盖级联是否残留。 |
| "4 万行里有多少是你写的？" | 服务端全部自研（HTTP 服务器、JSON、SHA-256、PBKDF2、SQLite 封装、日志、配额）；客户端用 Qt 6 与 SQLite 官方库，业务代码自研。第三方的角色是基础设施，不是业务实现。 |
| "端到端没测，那你怎么保证能用？" | 我不回避：目前验证到的是纯逻辑层、元数据层与构建纪律层，HTTP 端到端和 GUI 交互是空白。这也是我认定的第一优先级补齐项，论文里已如实标注。 |
| "你的测试是自己测自己吗？" | 密码学部分用的是公开标准向量（PBKDF2 6/0、认证 33/0 这类已公布值），不是自造输入自比对；数据库迁移用红→绿对照复现根因。 |
| "同步会不会把文件传丢？" | 三条硬规则：云端删除只进回收站；本地删除先搬 `sync-trash`，搬移失败逐个回退报错、绝不硬删；冲突保留两份不覆盖。 |
| "这个工作量一个人做得完吗？" | 我用的是"少做但做透"的策略：功能域裁到 8 个，界面 9 个页面，宁可砍功能也不留半成品模块。 |

## 7. 现场流程话术

**开场**：「各位老师好，我的毕业设计题目是《云匣——个人私有云网盘系统的设计与实现》。」

**被要求"简单说一下"** → 用 §0 的一句话定位 + 三条底线原则，30 秒收。

**被要求"详细讲讲"** → 按 §2 逐章讲，**每章末尾停顿 1 秒**给老师提问的窗口。

**被打断/质疑** → 先复述确认（"老师您问的是……对吗？"），再答；答不上来时：「这个我目前没有做到那一层，我的实现是……，如果要做我会先……」（**承认边界 + 给出思路**，不要硬编）。

**超时急救**：优先砍 M7、M8 各一句；**亮点段和局限段绝对不能砍**。

**结束语**：「我的汇报完毕 thanks各位老师。我的设计的核心就三件事：内容寻址解决存储成本与传输效率，双向同步的绝不丢数据原则解决可靠性，双库加归属隔离解决多用户安全。三件事各自都有代价，代价我在正文里都写清楚了。谢谢！」

**致谢**：「感谢指导教师在选题、方案论证到系统实现全过程中的悉心指导，也感谢各位老师提出中肯的意见。」
