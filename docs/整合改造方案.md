# 云匣 CloudVault · 客户端整合改造方案

> 本文是"整合"的**决策与执行总纲**：先厘清仓库里两套客户端的事实，再给出三条可选路线与推荐路线、缺口清单、清理清单与分阶段计划。
> 所有结论均附**实测证据**（命令输出或 file:line）；UI 细节见 [`UI优化方案.md`](UI优化方案.md)。

## 一、事实澄清：仓库里有两套客户端，且都不是"半成品"那么简单

| 维度 | `src/`（File.pro · qmake） | `client/`（CMake） |
|---|---|---|
| 定位（文档口径） | PRD **L10/L426**、TECH-STACK **L9/L35** 均指向它：**"桌面客户端"、Qt 6.8 LTS（C++17 + **QML** + Quick Controls）** | 团队文档一直称 **"Qt6 测试客户端"**；`docs/README.md` 只引用 `client/README.md` 作为客户端文档 |
| 技术栈 | Qt6 **QML** + QuickControls2（Fluent WinUI3 计划）、`qtquickcompiler`、SQL（本地索引）、Concurrent；分层 `core/net/sync/transfer/data/controllers/app` + `qml/` | Qt6 **Widgets** + Network；`MainWindow.cpp` 2969 行 + `FileTreeDialog.cpp` 607 行（合计 4038 行） |
| 代码实况 | **骨架**：`.pri` 声明 58 个文件，**实际存在 22、缺失 36** | **功能闭环**：上传（整文件+分块+断点续传）、下载（Range 并发+续传）、列表、预览、新建/重命名/删除/打开文件夹/排序、同名覆盖、存储空间、Bearer 令牌、TOFU 证书指纹固定 |
| 能否构建 | **否**：缺 `main.cpp`、`Application.*`、7 个 controller、6 个 QML model、`TransferManager`、`SyncEngine/FileWatcher`，且 **`qml/` 目录完全不存在**、`resources/quickcontrols2.conf` 也不存在；`bin/` 为空 → **从未产出过可执行文件** | 是：`cmake --build` 通过（本会话多次验证，最新 exe 597,017 B，0 error/0 warning） |
| 与另一套的关系 | **零交叉引用**（互不包含对方头文件）→ 可自由合并/替换 | 同上 |

### 1.1 `src/` 缺口明细（`.pri` 声明 vs 实际，Python 严格核对）

| 模块 | 存在 | 缺失 |
|---|---|---|
| `src/core` | 12（AppPaths/Async/Crypto/Logging/Settings/Types/Util） | 0 ✅ |
| `src/net` | 7（`Backend.h`、`HttpBackend.*`、`Json.*`、`MockBackend.*`） | 0 ✅ |
| `src/sync` | 3（`LocalIndex.*`、`SyncRules.h`） | **5**：`SyncRules.cpp`、`FileWatcher.*`、`SyncEngine.*` |
| `src/app` | 0 | **3**：`main.cpp`、`Application.h/.cpp` |
| `src/transfer` | 0 | **2**：`TransferManager.h/.cpp` |
| `src/controllers` | 0 | **14**：App/Auth/File/Share/Stats/Sync/Transfer 各 `.h/.cpp` |
| `src/data` | 0 | **12**：FileList/ShareLink/SyncPair/Tag/Transfer/Version 各 `.h/.cpp` |
| `qml/` | 不存在 | 界面层（theme/controls/pages/dialogs）**整层缺失** |
| **合计** | **22** | **36（+ 整个 qml 层）** |

补充观察：`MockBackend.cpp` **1089 行** > `HttpBackend.cpp` **513 行** —— `src/net` 原本是按 Mock 驱动开发的；`src/` 全仓 **0 个 TODO/FIXME**，说明它是"设计先落地、实现未跟进"的骨架，而非写坏的半成品。

### 1.2 产品需求对客户端的硬要求（PRD / AC）

- FR-9-2：桌面客户端 = **后台同步引擎 + 托盘 + 简化文件视图 + 传输队列**（P0）
- FR-2-3 / AC-09：10GB 文件断点续传，不重传已完成分块（P0）
- AC-01~AC-15：**同步对**、5 秒防抖入队、双端 10 秒一致、版本回溯、回收站、忽略规则（`.cvignore`）、改删冲突、1000 文件批量
- TECH-STACK：客户端 GUI = **Qt 6.8 LTS + QML**；构建 qmake → **CMake 迁移**（P0→P1）；测试 = Qt Test

→ 也就是说：**`src/` 的缺失层（sync / transfer / controllers / qml）恰好就是 PRD 的 P0 需求所在**；而 `client/` 已实现的是其中的**传输与安全部分**，但**没有同步引擎、托盘、版本、回收站**。

## 二、三条路线对比（请拍板）

| | **路线 A（推荐）** 能力母体 + 目标架构 | 路线 B 只保 `src/` | 路线 C 只保 `client/` |
|---|---|---|---|
| 做法 | 把 `client/` 已验证的协议层抽成可复用内核（`ApiClient` + `TransferEngine`），**先让 `client/` 重构为正式产品**（Widgets 现代化 UI），同时把内核对齐 `src/net`+`src/transfer`；随后按 `src/` 分层补齐 app/data/controllers，最后补 `qml/` | 以 `src/` 为准，**从零补齐 36 个文件 + 整个 qml 界面层**，`client/` 直接删除 | 只保留 `client/`，改名为正式客户端，删除 `src/` 骨架与 MockBackend |
| 可交付时间 | 阶段 A 即可交付"现代化正式客户端"，后续平滑演进 | 长（等于新写一个客户端 UI + 同步引擎） | 最短 |
| 风险 | 中（需在 Widgets 与 QML 间做一次迁移） | **高**（36 文件 + qml 层从零写，无中间可运行版本） | 中（放弃 PRD 的 QML/同步引擎愿景，后续要重做 UI） |
| 与 PRD/TECH-STACK 一致性 | 逐步达成（最终仍是 QML） | 完全一致 | 不一致（UI 技术栈偏离选型） |
| 我的判断 | ✅ **推荐**：先把已有价值固化为产品，再按目标架构演进 | ⚠️ 仅当你确定要"推倒重来"且能承受周期 | ⚠️ 仅当你决定放弃 QML 路线 |

**推荐路线 A 的关键点**：不要"重写"，而是**先抽内核、再做界面、最后换外壳**——每一步都保持可运行、可验证。

## 三、路线 A 的分阶段执行计划

### 阶段 A · 内核抽取 + 界面现代化（可独立交付）
| 步骤 | 内容 | 产出/验收 |
|---|---|---|
| A1 | 把 `client/src/MainWindow.cpp` 中的**协议与传输逻辑**抽出：`ApiClient`（URL 拼装、Bearer 令牌注入、TLS/TOFU 证书策略、错误映射、401/409/416/507 语义）、`TransferEngine`（分块上传+断点续传、Range 并发下载、秒传、同名覆盖决策） | 新文件 `client/src/core/ApiClient.*`、`client/src/core/TransferEngine.*`；**行为不变**（回归清单全过） |
| A2 | 把 UI 拆为组件：`ConnectionBar` / `ToolBar` / `FileListView` / `PreviewPane` / `LogPane`（`MainWindow.cpp` 2969 行 → 各 200–400 行） | 编译 0 error/0 warning；右键菜单 7 项、TOFU、令牌、分块/续传全部可用 |
| A3 | 落地设计系统：`Theme.h` + `resources/theme.qss` + `app.qrc`（详见 `UI优化方案.md` P1） | 风格统一；窄屏 720×520 无横向滚动 |
| A4 | 响应式与三态（详见同一文档 P2/P3） | 三档断点、空/载/错态、快捷键 |

### 阶段 B · 对齐目标架构（`src/`）
| 步骤 | 内容 |
|---|---|
| B1 | 把阶段 A 的 `ApiClient` / `TransferEngine` **对齐并编入 `src/net` + `src/transfer`**（补 `TransferManager.*`），去重（`HttpBackend` 与 `ApiClient` 合一） |
| B2 | 补 `src/app`（`main.cpp` + `Application.*`）+ `src/controllers`（先 `AppController`、`FileController`、`TransferController`） |
| B3 | 补 `src/data` 模型（`FileListModel`、`TransferModel` 先行） |
| B4 | 构建迁移：qmake → **CMake**（TECH-STACK P0→P1），统一三端构建 |

### 阶段 C · 正式客户端成型（PRD P0 需求）
| 步骤 | 内容 |
|---|---|
| C1 | 补 `qml/`（theme/controls/pages/dialogs），承接阶段 B 的 controllers/models；UI 风格承接阶段 A 的设计令牌（**视觉一致**） |
| C2 | 同步引擎：`SyncEngine` + `FileWatcher`（+ `SyncRules.cpp` 忽略规则 `.cvignore`）→ 满足 AC-01/02/03/06/08 |
| C3 | 托盘 + 传输队列 + 自动重试 → FR-9-2、AC-11 |
| C4 | 版本回溯 / 回收站 / 标签 / 配额告警（依赖服务端能力，需另立需求） |

### 阶段 D · 测试客户端退役与仓库清理
| 项 | 处置 |
|---|---|
| `client/` | 二选一：① 保留为 `tools/devclient/`（**联调工具**，仅内部用，不进发布包）；② 按你的要求**彻底删除**（对应"移除对测试客户端的依赖 + 清理测试用代码与配置"） |
| 应用命名 | `client/src/main.cpp:19` 现为"云匣 CloudVault **测试客户端**" → 若保留则改名；正式客户端用 `src/` 的 `Application` 显示名 |
| 构建产物（**清理清单**） | `build/`(10 文件)、`build_now/`(4)、`output/`(1)、`bin/`(空)、**`client/` 下 19 个 `build*` 目录**、`client/build_sec2` 等 → 移入 `.gitignore` 并删除；`File.pro.user`（IDE 私有配置）应 ignore |
| 文档改指 | `docs/README.md` 现把 `client/README.md` 当作客户端文档 → 阶段 B 后改指 `src/`/新建的正式客户端文档；`docs/测试用例-*.md` 中的"客户端按钮"用例在阶段 D 一并重写 |
| Mock 后端 | `MockBackend.cpp`(1089 行) 保留为**开发/离线模式**（`--mock`），但默认主流程必须走 `HttpBackend`（"真实主流程"要求） |
| 导出配置 | `resources/quickcontrols2.conf` **不存在** → 阶段 C1 需新建（Fluent WinUI3 样式） |

## 四、需要保留的既有资产（不得丢失）

1. **服务端契约与实现**（`server/`，含 TLS/鉴权/静态加密/keep-alive 与 `server/tests/` 验收脚本）——整合过程**零改动**。
2. **已修复的安全语义**：TOFU 指纹固定（含 `box.exec()` 正确弹窗）、Bearer 令牌、证书查看/清除入口。
3. **已验证的传输能力**：5MiB 分块、断点续传、8MiB×4 路并发 Range 下载、秒传、同名覆盖询问（含 `X-CV-Overwrite`/`overwrite:true` 契约）。
4. **文档与验收基线**：`PRD`、`TECH-STACK`、`AC-同步用户故事验收标准15条`、`大文件传输设计.md`、`server/tests/`。
5. **原有 UI 交互**（若选路线 A）：右键菜单 7 项、键盘/预览/日志等已在用习惯。

## 五、风险与注意事项

| 风险 | 说明 | 缓解 |
|---|---|---|
| `src/` 缺口被低估 | 36 文件 + qml 层 = 一个客户端的完整 UI/同步实现 | 用路线 A 分阶段交付，避免"半年无可运行版本" |
| 两套 UI 技术栈并存 | 阶段 A（Widgets）→ 阶段 C（QML）会出现"界面重做" | 阶段 A 就把**设计令牌与信息架构**固化到文档/常量，QML 侧复用同一套令牌与页面结构 |
| 构建迁移 qmake→CMake | 影响三端 | 放在阶段 B 末尾（功能冻结窗口），与 TECH-STACK 建议一致 |
| 清理误删 | `client/` 下 19 个构建目录、`File.pro.user` 等 | 清理只动**产物与 IDE 配置**，源码一律先 `git mv`/先提交再删；删除前列清单二次确认 |
| 单人维护成本 | 两条客户端同时存在会持续分叉 | 阶段 A 起就明确 `client/` 的"工具"定位，禁止在其上新增业务功能 |
