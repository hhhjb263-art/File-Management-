# 云匣 CloudVault 双客户端整合方案

## 0. 结论摘要（必读）

**`src/` 不是"旧原型"，而是正式客户端 `CloudVault v0.5.0` 的产品蓝图 + 部分地基；但它的 UI 层与大部分 C++ 层文件根本不存在。**

| 事实 | 证据 |
|---|---|
| `src/` 目标形态是 **QML 现代界面** | `config.pri:9` `QT += core gui qml quick quickcontrols2 network sql concurrent`；`resources/qtquickcontrols2.conf`（FluentWinUI3 风格） |
| 它的**分层骨架已定义、文件缺失** | `src/app/app.pri` 声明 `Application.h/.cpp` + `main.cpp`；`src/controllers/controllers.pri` 声明 7 个控制器；`src/transfer/transfer.pri` 声明 `TransferManager`（注释写明"分块/秒传/断点续传/并发控制"）；`src/data/data.pri` 声明 6 个 QML 数据模型 —— **以上文件全部不存在** |
| **没有任何 QML 文件** | 全仓 `find -name "*.qml"` 为空 → UI 完全未写 |
| 已实现的只有三层 | `core/` 1084 行（AppPaths/Async/Crypto/Logging/Settings/Types/Util）、`net/` 2212 行（Backend 抽象/HttpBackend/Json/**MockBackend**）、`sync/` 281 行（LocalIndex/SyncRules） |
| `client/`（Widgets）是**当前唯一能跑**的客户端 | `client/src/MainWindow.cpp` 2969 行单体，全部功能已在真机验证 |

**所以"整合"的真实内容 = 以 `src/` 的正式架构为主干，把 `client/` 已验证的能力对齐进去，补齐缺失的控制器/传输/数据模型/QML 界面，最后移除对测试客户端的依赖。**

---

## 1. 关键差距：`Backend` 抽象 vs 服务端真实能力

`src/net/Backend.h` 定义的抽象接口是**产品级**的（44+ 方法），但服务端目前只实现其中一部分：

| `Backend` 抽象要求 | 服务端现状 | 结论 |
|---|---|---|
| `login/logout/currentUser` | **无**（服务端只有 `--auth-token` 单一令牌，无用户体系） | ⚠️ 缺口 |
| `listFolder/listUnderPath` | ✅ `GET /api/v1/files`、`GET /api/v1/tree` | 可对齐 |
| `statById/statByPath` | ✅ `GET /api/v1/files/:id`、`GET /api/v1/download?path=` | 可对齐 |
| `createFolder/ensureFolderPath` | ✅ `POST /api/v1/dirs` | 可对齐 |
| `rename` | ✅ `POST /api/v1/files/:id/rename` | 可对齐 |
| `moveToTrash/restore/purge/emptyTrash/listTrash` | ⚠️ 只有软删除 `DELETE /api/v1/files/:id`，**无回收站查询/还原/清空接口** | ⚠️ 缺口 |
| `beginUpload/putChunk/finishUpload/cancelUpload` | ✅ `POST /uploads/init`、`PUT /uploads/:id/chunk/:seq`、`POST /uploads/:id/complete`、`DELETE /uploads/:id` | ✅ 完全对应 |
| `getRange` | ✅ `GET /files/:id/content` + `Range` | 可对齐 |
| `versions/restoreVersion` | **无** | ⚠️ 缺口 |
| `shares/createShare/revokeShare/touchShare` | **无** | ⚠️ 缺口 |
| `tags/createTag/deleteTag/setTags` | **无** | ⚠️ 缺口 |
| `search` | **无**（仅客户端本地排序） | ⚠️ 缺口 |
| `usage` | ✅ `GET /api/v1/storage` | 可对齐 |

> 这解释了项目现状：**正式客户端的设计目标远超服务端当前能力**，所以才有"测试客户端"先行验证服务端。
> `HttpBackend.cpp` 目前只覆盖了其中一部分（关键词扫描：`chunk`×2、`Range`×5、`token`×8；`init`/`complete`/`resume`/`fingerprint` 等为 0），需要逐方法核实覆盖率。

## 2. 整合方案（四步）

### 第 1 步 · 能力面裁剪与对齐（先做，避免建在沙上）
- 逐方法核实 `src/net/HttpBackend.cpp` 对 `Backend.h` 的实现覆盖率，产出**"已实现 / 桩实现 / 未实现"**清单
- 对服务端不具备的能力（登录、回收站、版本、分享、标签、搜索）：**在抽象层保留接口，但明确标注 `unsupported`，UI 不暴露入口**；或按需在服务端补齐（另立任务）
- 对齐服务端真实契约细节（`Bearer` 令牌、`X-CV-*` 头、409 同名冲突、416/507 等错误语义、TOFU 证书固定）——这些在 `client/` 里都已验证过，直接迁移逻辑

### 第 2 步 · 从 `client/` 迁移已验证逻辑（不复制 UI）
| 能力 | 迁移目标 | 来源（已实现且验证过） |
|---|---|---|
| 分块上传 + 断点续传（manifest/续传判定/并发 3 块/分块哈希） | `src/transfer/TransferManager` | `client/src/MainWindow.cpp`（`beginChunkedUploadFor`/`launchChunkAsync`/pump/manifest） |
| Range 并发下载（4 路窗口、按序落盘、断点） | 同上 | `client/src/MainWindow.cpp`（`pumpDownload`/`drainDownloadReady`/`maybeStartWrite`） |
| TOFU 证书指纹固定（4 条决策路径 + 日志） | `net/HttpBackend` + `core/Settings` | `client/src/MainWindow.cpp:applyCertPinning`（含 `box.exec()` 教训） |
| 令牌鉴权注入（Bearer，4 处连接点） | `net/HttpBackend` 统一出口 | `client/src/MainWindow.cpp:sendRequest` + `FileTreeDialog::applyAuthToken` |
| 同名检测交互（409 → 覆盖/跳过） | `controllers/FileController` | `client/src/MainWindow.cpp:askOverwrite` |
| 存储空间/日志/设置持久化 | `core/Settings`、`controllers/StatsController` | `client/` 与 `src/core/Settings` 合并 |

### 第 3 步 · 补齐缺失层（本次工作量大头）
- `app/`：`main.cpp` + `Application`（装配 Backend/Controllers/Models，加载 QSS/主题）
- `controllers/`：7 个控制器（QML 的唯一入口，界面不直接碰后端）
- `data/`：QML 数据模型（`FileListModel`、`TransferModel` 等）
- QML 界面（现代 + 响应式）：主窗口（连接栏 / 文件列表 / 传输队列 / 详情预览 / 设置）、右键菜单、对话框；三档断点布局（≥1280 / 768–1280 / <768），沿用 `docs/UI优化方案.md` 的设计令牌

### 第 4 步 · 移除测试客户端与清理
- 删除 `client/`（源码 + 全部 `build*` 目录）与仅服务测试的配置
- 清理构建产物：`bin/`、`build/`、`build_now/`、`output/`（先确认无引用再删，并补 `.gitignore`）
- 保留 `server/tests/*`（服务端验收脚本，与客户端无关）
- 文档同步：README 指向正式客户端；`docs/` 标注测试客户端的退役

## 3. 需要用户决策的两点

1. **`Backend` 抽象中服务端不具备的能力（登录/回收站/版本/分享/标签/搜索）如何处理？**
   - A. 抽象层保留、标注 unsupported、UI 暂不暴露（最快让正式客户端可用）
   - B. 先砍掉这些接口，只保留服务端能做的（最简洁，但偏离产品蓝图）
   - C. 同步扩展服务端补齐这些接口（最完整，工作量最大）
2. **QML 界面首版范围？**
   - A. 核心可用（连接设置 + 文件列表 + 上传/下载 + 传输队列 + 日志）
   - B. 核心 + 同步（LocalIndex/SyncRules 已有地基）
   - C. 全量（含分享/标签/版本/回收站，需先解决决策 1）

## 4. 风险

- `src/` 的 `.pri` 声明的文件**全部缺失**，若直接 `qmake` 会立即失败 → 必须先补齐或临时调整 `.pri` 才能编译验证
- `MockBackend`（`src/net/MockBackend.cpp`）是测试替身，需确认保留（本地引擎模式）还是收敛
- 服务端 `Backend` 契约的**错误语义**（401/409/416/507）必须在 `HttpBackend` 中完整映射，否则 UI 无法给出正确提示
